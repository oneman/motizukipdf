# PIPELINE

The whole theory, run once on real numbers. `iut pipeline` takes one set of initial Θ-data
and carries it through every construction the toolkit implements, printing the state after
each stage:

| stage | what is built | reference |
|---|---|---|
| 0 | the initial Θ-data (F̄/F, X_F, l, C̲_K, V, V^bad_mod, ε̲), with the Tate parameter q_v = p^ord · u at every v ∈ V^bad_mod | [IUTchI] Def 3.1 |
| 1 | the conditions (a)–(f) of Def 3.1, each with how it was checked | [IUTchI] Def 3.1 |
| 2 | the Θ±ell NF-Hodge theater: the Θ±ell-HT (capsule of l F-prime-strips, symmetry F_l^{⋊±}), the ΘNF-HT (capsule of l* strips, symmetry F_l^*), the gluing, the Θ-Hodge theater at V^bad and the prime-strips at (0,0) | [IUTchI] §3–§6, Def 6.13 |
| 3 | the Gaussian monoids: the theta values q̲_v^{j²}, j = 1..l*, with their orders and units mod p^8, and the log-volumes of the q-pilot and the Θ-pilot | [IUTchII] Cor 2.5, 3.5, 4.10 |
| 4 | the log-theta-lattice ("infinite H"): Hodge theaters at (n, m), the Θ×μ_LGP-link (0,0) → (1,0), the log-links and the log-shells I_v they build | [IUTchIII] Def 1.1, 1.4, 3.8 |
| 5 | the multiradial representation: the procession of tensor packets, the indeterminacies (Ind1)–(Ind3), and the inequality of Cor 3.12 | [IUTchIII] Thm 3.11, Cor 3.12 |
| 6 | the height bound of Thm 1.10 and the conditions of Cor 2.2 | [IUTchIV] Thm 1.10, Cor 2.2 |
| 7 | a cross-check: log q, \|log q\|, log f and ht computed by the toolkit against the values stored in the JSON file | — |

The exit status is the number of problems (Def 3.1 errors, Hodge-theater and lattice
validation errors, cross-check mismatches, and Cor 3.12 failing), so `0` means every stage
went through.

## Running it

```sh
make -C src
src/iut pipeline --theta-json docs/initial-theta-data/frey-1-8-9.json          # text, stage by stage
src/iut pipeline --theta-json docs/initial-theta-data/frey-1-8-9.json --json   # schema iut-pipeline/1
src/iut pipeline --abc 1 2400 2401 --l 11                                       # any other data option works too
node scripts/pipeline/build.js                                                  # regenerate the files below
```

`--theta-json` takes a file in the schema `iut-initial-theta-data/1` (or the JSON text itself,
if it starts with `{`). It is accepted by every command that takes data (`gen`, `validate`,
`walk`, `run`, `pipeline`, `tui`). The parser is `src/iut_input.c`; the pipeline is
`src/iut_pipeline.c`. `--rows R` sets how many rows of the lattice are built (default 2) and
`--horizontal` chooses the horizontal link (default the Θ×μ_LGP-link).

In the web app, the **Pipeline** view runs the same code (compiled to WebAssembly) and draws
each stage; the bar at the top has an *exact Θ-data (JSON)* option that loads the four examples
below (`htdocs/data/initial-theta-data.js`, generated by `scripts/pipeline/build.js`).

How to read the columns: *log q* = Σ_{v ∈ V^bad_mod} ord_v(q_v) log p_v and |log q| = log q / 2l.
The *Θ-pilot log-volume* is −(l(l+1)/12)·|log q|, the average of the theta values q̲^{j²}
over j ∈ F_l^*. *Σ leading terms* is the procession-normalized hull of step (4) of Cor 3.12.
*C_Θ* is the constant with −|log Θ| ≤ C_Θ · |log q|, and Cor 3.12 asks C_Θ ≥ −1.

## What the numbers say

* Every example satisfies Def 3.1 and builds a valid Θ±ell NF-Hodge theater and a valid
  lattice (10 Hodge theaters, 8 log-links and 1 Θ-link for two rows above and below).
* The toolkit's log q, |log q|, log f and ht agree with the values computed independently
  from the curve and stored in the JSON files.
* For curves this small the inequality of Thm 1.10 holds with an enormous margin and says
  nothing sharp: its right-hand side is about 10^22 because of the constant η_prm = 5·10^20
  ([IUTchIV] Thm 1.10), against (1/6) log q between 0.7 and 10.5 here.
* For 2 + 3¹⁰·109 = 23⁵ with l = 7, condition (C1) of Cor 2.2 is out of range (it needs
  l ≥ 7.919); the pipeline reports this as information, not as a problem, since Thm 1.10 itself
  does not need it.

## Two fixes this needed

* **ε̲ is a cusp from a nonzero element.** Def 3.1 (f) asks for a cusp of C̲_K that arises
  from a *nonzero* element of Q ≅ Z/lZ, and at v ∈ V^bad the cusp of the canonical generator,
  ±1. The toolkit used to store ε̲ = 0. It now stores the label 1 ∈ F_l^* (the cusp ±1),
  and the validator reports an error for 0 or for a label other than ±1 when V^bad is not empty.
* **log q is summed over V^bad_mod only.** [IUTchIV] Thm 1.10 sums ord(q_v) log p_v over
  V^bad_mod, which excludes the places above 2 (Rem 1.10.6 (i)); the toolkit used to include
  them. The places above 2 now count only in log q∀ of Cor 2.2. For 1 + 2400 = 2401 this moves
  log q from 25.5886 to 24.2023 = 2 log 3 + 4 log 5 + 8 log 7. Likewise the tempered
  Frobenioids, theta bridges and Gaussian monoids are built at V^bad (odd places of bad
  multiplicative reduction) and no longer at v2.

## Limitations

* The JSON files do not record the local ramification of K = F(E[l]), so the pipeline takes
  e(K_v/Q_p) = 1 and the log-shells come out as p^0·O_v (μ_log 0) at every finite place.
* log d^K is an estimate, log d^F + log f_Q + 2 log l, since the exact discriminant of K is not
  known; it enters only the hull of step (4).
* When a file gives no log-different for F_tpd, log d^{F_tpd} is taken as 0.
* The Tate parameter's unit u is known mod p^8 (or less if p^8 would overflow 62 bits); the
  units of q_v^{j²} are computed in that precision.
